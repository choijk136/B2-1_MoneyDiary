# 저장 포맷 결정과 100k 성능 분석

이 문서는 저장 포맷 선택 근거와 100,000건 데이터에서 측정한 병목 및 개선 계획을 기록한다. 측정은 재현 가능한 `scripts/benchmark_100k.py`로 수행했다.

## 1. JSONL과 CSV 비교

| 비교 항목 | JSONL | CSV |
| --- | --- | --- |
| 스트리밍 | 한 줄이 독립된 JSON 객체라 줄 단위 생성·소비가 쉽다. 파일 끝에서 역방향으로 읽기도 쉽다. | `csv` 모듈로 행 단위 처리가 가능하지만, 인용된 필드의 쉼표·줄바꿈 때문에 단순 줄 분리가 안전하지 않다. |
| 자료형 | 숫자, 문자열, 배열을 구분한다. `tags`를 JSON 배열로 직접 저장할 수 있다. | 모든 값이 셀이므로 `tags`를 쉼표 문자열로 별도 인코딩·파싱해야 한다. |
| 스키마 변경 | 각 레코드에 필드명이 있어 선택 필드를 추가하기 쉽고 누락 필드를 기본값으로 처리할 수 있다. | 헤더 순서와 열 이름을 함께 관리해야 하며 스키마 변경 시 기존 행과의 호환 처리가 필요하다. |
| 사람이 읽기/편집 | 한 행이 길지만 필드 의미가 자체적으로 드러난다. | 표 계산 프로그램에서 열기 쉽고 반복되는 필드명이 없어 일반적으로 더 작다. |
| 손상 격리 | 손상된 줄의 위치를 특정하기 쉽고 다른 줄과 독립적으로 복구할 수 있다. | 따옴표나 줄바꿈이 손상되면 이후 행 경계까지 영향을 줄 수 있다. |
| 추가(add) | 파일 끝에 JSON 객체 한 줄을 append하고 `fsync`하면 된다. | 파일 끝에 CSV 행을 append할 수 있다. 헤더와 quoting 규칙을 계속 유지해야 한다. |
| 수정/삭제 | 가변 길이 레코드라 제자리 수정이 어렵고 임시 파일로 재작성해야 한다. | 마찬가지로 행 길이가 달라질 수 있어 안전한 수정/삭제에는 전체 재작성이 필요하다. |
| 외부 호환성 | API·프로그램 간 교환에 적합하지만 스프레드시트 사용성은 낮다. | Excel 등에서 바로 열 수 있어 사용자 데이터 교환에 유리하다. |

### JSONL 선택 이유

내부 영구 저장에는 **JSONL**을 선택했다. 거래의 `tags`를 문자열로 손실 변환하지 않고 배열로 저장할 수 있고, 한 줄이 독립된 객체라 `yield` 기반 순차 처리와 파일 끝에서 시작하는 최신순 역방향 스트리밍을 함께 구현하기 쉽기 때문이다. 필드명이 레코드에 포함되어 `memo`·`tags` 같은 선택 필드의 기본값 처리와 향후 스키마 확장도 명확하다.

JSONL도 update/delete에서 전체 재작성이 필요하고 CSV보다 파일이 커질 수 있다는 단점이 있다. 이 애플리케이션은 이를 임시 파일 기록 → `flush`/`fsync` → `os.replace` 순서의 원자적 교체로 보완한다. CSV의 높은 외부 호환성은 버리지 않고 import/export 경계 포맷으로 사용한다. 즉, **내부 안전한 스트리밍 저장은 JSONL, 사용자 교환은 CSV**로 역할을 분리했다.

## 2. 100,000건 프로파일링 방법

다음 명령은 임시 폴더에 100,000건을 만들고 종료 시 모두 삭제한다. 테스트 데이터 생성 시간은 각 연산 측정에서 제외한다. 표의 최대 메모리는 Python 표준 라이브러리 `tracemalloc` 기준이며, 시간에는 `tracemalloc` 계측 오버헤드가 포함되어 있어 절대값보다 연산 간 상대 비교에 의미가 있다.

```bash
python -m scripts.benchmark_100k --records 100000
```

측정 환경과 데이터:

- Python 3.12.14
- Linux 6.18.35 x86_64, glibc 2.39
- 거래 100,000건, `transactions.jsonl` 15.68 MiB
- 단일 프로세스·로컬 파일시스템, 각 연산 1회 측정

## 3. 측정 결과

### 개선 후 결과

| 연산 | 시간(초) | 최대 메모리(MiB) | 처리 결과 |
| --- | ---: | ---: | ---: |
| `list(limit=20)` | 0.001 | 0.03 | 20건 |
| `search(category=food)` | 2.661 | 0.14 | 12,500건 |
| `summary(month=2024-01)` | 2.791 | 0.13 | 100,000건 집계 |
| `get(missing-id)` | 2.627 | 0.14 | 전체 조회 후 없음 |
| `update(oldest-id)` | 13.826 | 0.69 | 1건 수정 |
| `delete(missing-id)` | 11.238 | 0.68 | 전체 확인 후 없음 |
| `export(month=2024-01)` | 3.612 | 0.29 | 100,000건 |

메모리 사용량이 낮은 이유는 저장소·검색·CSV export가 거래를 한 건씩 `yield`하기 때문이다. `list(limit=20)`은 역방향 블록 읽기와 `islice`가 결합되어 거래 수가 늘어도 필요한 20건만 역직렬화한다.

### cProfile 결과

전체 카테고리 검색은 계측 오버헤드가 더 작은 별도 `cProfile` 실행에서 1.642초, 약 493만 함수 호출이었다. 누적 시간 기준 호출 경로는 다음과 같았다.

| 호출 경로 | 호출 수 | 누적 시간(초) | 해석 |
| --- | ---: | ---: | --- |
| `search_transactions` | 12,501 | 1.636 | 결과를 yield하기 전 100k 전체를 검사 |
| `iter_transactions` | 100,001 | 1.610 | 모든 JSONL 레코드를 순회 |
| `Transaction.from_dict` | 100,000 | 1.010 | 딕셔너리를 모델로 변환·검증 |
| `json.loads` | 100,000 | 0.362 | JSON 디코딩 비용 |

초기 구현은 레코드를 읽을 때마다 `datetime.strptime`을 호출했다. 동일 조건에서 검색 7.938초, 요약 7.895초, 없는 ID 조회 7.825초였다. 엄격한 ISO 형식을 확인하는 `date.fromisoformat`으로 교체한 후 각각 2.661초, 2.791초, 2.627초로 감소했다. `YYYY-M-D`처럼 0이 생략된 입력도 추가로 거부하므로 검증 정확도도 높아졌다.

또한 초기 출력 포맷터는 열 너비 계산을 위해 검색 결과를 `list`로 만들었다. 현재는 고정 폭 행을 생성하는 `iter_transaction_lines()`로 변경하여 검색 결과도 마지막 출력 단계까지 한 행씩 처리한다. `tests/test_formatters.py`에서 첫 출력 시 첫 거래만 소비하는지 검증한다.

## 4. 확인된 병목

1. **조건 검색·요약은 O(n) 전체 순회**  
   카테고리·월 조건이 있어도 100,000줄을 모두 JSON 디코딩하고 `Transaction`으로 만든다. cProfile에서 `iter_transactions`와 `from_dict`가 대부분의 시간을 차지했다.

2. **ID 조회도 O(n)**  
   현재 JSONL에 ID 위치 정보가 없으므로 오래된 ID나 없는 ID는 파일 전체를 읽는다. `update`는 대상 조회 후 다시 전체 파일을 재작성하므로 두 번의 전체 순회가 발생한다.

3. **update/delete의 전체 파일 재작성**  
   안전한 원자적 교체를 위해 모든 생존 레코드를 임시 파일에 JSON으로 다시 기록한다. 따라서 CPU 디코딩·인코딩과 디스크 쓰기가 함께 발생한다. 실제로 가장 느린 연산은 오래된 거래 update 13.826초와 없는 ID delete 11.238초였다.

4. **대량 import의 반복 ID 확인**  
   `add_transaction()`은 UUID를 만든 뒤 기존 ID와 충돌하는지 파일을 검색한다. CSV의 각 행마다 실행하면 데이터가 커질수록 반복 전체 검색이 발생할 수 있다. 이는 코드 경로 분석으로 확인한 잠재적 O(n²) 병목이다.

5. **단일 파일·단일 프로세스 처리**  
   현재는 데이터 일관성을 단순하게 유지하기 위해 하나의 거래 파일을 한 프로세스에서 처리한다. 수백만 건에서는 JSON 파싱 CPU와 단일 파일 재작성 시간이 함께 증가한다.

## 5. 구체적 개선안

### 1순위: 보조 인덱스

- `transaction_index.jsonl`에 `id -> byte offset`을 기록하고, `month/category/date -> offset 목록`의 보조 인덱스를 둔다.
- `get(id)`는 인덱스에서 offset을 찾은 뒤 `seek()`하여 평균 O(1)에 접근한다. 조건 검색은 전체 n건 대신 후보 k건만 읽는 O(k)가 된다.
- 인덱스에는 대상 `transactions.jsonl`의 크기·수정 시각·세대 번호를 기록한다. 불일치하거나 손상되면 원본 JSONL을 한 번 순회해 재구축하므로 인덱스가 진실의 원본이 되지 않게 한다.
- update/delete의 원자적 교체가 끝난 다음 새 인덱스를 임시 파일에서 교체한다. 두 파일의 세대가 다르면 시작 시 자동 재구축한다.

### 2순위: 청크화와 로그 구조

- 거래를 월별 또는 최대 64 MiB 청크(`transactions-2024-01-0001.jsonl`)로 나누고 manifest에 순서를 기록한다.
- update/delete는 전체 데이터 대신 ID 인덱스가 가리키는 청크만 원자적으로 재작성한다.
- 더 큰 규모에서는 수정·삭제를 기존 줄의 제자리 변경 대신 append-only 이벤트 또는 tombstone으로 추가하고, 일정 임계치에서 청크 단위 compaction을 수행한다. 평상시 쓰기는 O(1)에 가깝게 유지된다.

### 3순위: 집계 캐시와 대량 import 배치

- 월별 수입·지출과 카테고리 합계를 별도 캐시에 유지하고 add 시 증분 반영한다. update/delete 때 관련 월만 무효화하거나 다시 계산한다.
- import 시작 시 기존 ID를 한 번만 `set`으로 구성하거나 UUID 충돌 인덱스를 사용한다. 입력은 예를 들어 10,000행 단위로 검증하고, 청크마다 한 번 `flush`/`fsync`한다.
- 각 청크의 `imported/skipped` 및 행별 오류를 모아 현재의 부분 성공 보고 방식은 그대로 유지한다.

### 4순위: 병렬화 적용 기준

- 파일을 청크화한 뒤 서로 독립된 청크의 검색·요약을 `concurrent.futures.ProcessPoolExecutor`로 병렬 처리하고, 부모 프로세스에서 부분 합계를 병합한다.
- JSON 디코딩은 CPU 작업이므로 스레드보다 프로세스를 사용한다. 하나의 디스크에서 작은 파일을 처리할 때는 프로세스 시작·I/O 경합 비용이 더 클 수 있으므로 1백만 건 이상에서 단일 프로세스와 재측정한 뒤 활성화한다.
- 결과 순서가 필요한 검색은 각 프로세스가 정렬된 결과 스트림을 반환하고 부모가 `heapq.merge`로 병합해 전체 결과 리스트 생성을 피한다.

## 6. 성능 회귀 확인

기능 테스트와 벤치마크를 순서대로 실행한다.

```bash
python -m unittest discover -v
python -m scripts.benchmark_100k --records 100000
```

벤치마크 수치는 하드웨어와 파일시스템에 따라 달라진다. 커밋 간 비교는 동일한 환경·레코드 수에서 수행하고, 최소 5회 실행의 중앙값을 사용하는 것이 적절하다. 이 문서의 수치는 평가자가 명령을 빠르게 재현할 수 있도록 1회 실측값을 그대로 기록했다.
