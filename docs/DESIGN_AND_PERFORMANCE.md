# 저장 포맷 결정과 100,000건 프로파일링

거래가 10만 건일 때 최신 20건 조회는 **0.22 ms**, 식비 검색은 **0.500초**, 가장 오래된 거래 한 건 수정은 **2.393초**였다(각 3회 중앙값). 식비 12,500건을 찾는 데 거래 객체를 100,000개 만들었고, 한 건을 수정할 때는 200,000개를 읽어 변환했다. 아래에 저장 형식을 선택한 이유, 실제 병목, 아직 적용하지 않은 개선안을 구분했다.

[원본 측정 결과(JSON)](evidence/profile-100k.json) · [실행 스크립트](../scripts/benchmark_100k.py) · [프로그램 사용법](../README.md)

## 1. JSONL과 CSV 비교

| 비교 항목 | JSONL | CSV |
| --- | --- | --- |
| 스트리밍 | 한 줄이 독립된 JSON 객체라 줄 단위 생성·소비가 쉽다. 파일 끝에서 역방향으로 읽기도 쉽다. | `csv` 모듈로 행 단위 처리가 가능하지만, 인용된 필드의 쉼표·줄바꿈 때문에 단순 줄 분리가 안전하지 않다. |
| 자료형 | 숫자, 문자열, 배열을 구분한다. `tags`를 JSON 배열로 직접 저장할 수 있다. | 모든 값이 셀이므로 `tags`를 쉼표 문자열로 별도 인코딩·파싱해야 한다. |
| 스키마 변경 | 각 레코드에 필드명이 있어 선택 필드를 추가하기 쉽고 누락 필드를 기본값으로 처리할 수 있다. | 헤더 순서와 열 이름을 함께 관리해야 하며 스키마 변경 시 기존 행과의 호환 처리가 필요하다. |
| 사람이 읽기/편집 | 한 행이 길지만 필드 의미가 자체적으로 드러난다. | 표 계산 프로그램에서 열기 쉽고 반복되는 필드명이 없어 일반적으로 더 작다. |
| 손상 격리 | 손상된 줄의 위치를 특정하기 쉽고 다른 줄과 독립적으로 복구할 수 있다. | 따옴표나 줄바꿈이 손상되면 이후 행 경계까지 영향을 줄 수 있다. |
| 추가(add) | 파일 끝에 JSON 객체 한 줄을 append하고 `fsync`하면 된다. | 파일 끝에 CSV 행을 append할 수 있다. 헤더와 quoting 규칙을 계속 유지해야 한다. |
| 수정/삭제 | 가변 길이 레코드라 제자리 수정이 어렵고 임시 파일로 재작성해야 한다. | 마찬가지로 행 길이가 달라질 수 있어 안전한 수정/삭제에는 전체 재작성이 필요하다. |
| 외부 호환성 | API·프로그램 간 교환에 적합하지만 스프레드시트 사용성은 낮다. | Excel 등에서 바로 열 수 있어 사용자 데이터 교환에 유리하다. |

### JSONL 선택 이유

내부 영구 저장에는 **JSONL**을 선택했다. 거래의 `tags`를 문자열로 손실 변환하지 않고 배열로 저장할 수 있고, 한 줄이 독립된 객체라 `yield` 기반 순차 처리와 파일 끝에서 시작하는 최신순 역방향 스트리밍을 함께 구현하기 쉽기 때문이다. 필드명이 레코드에 포함되어 `memo`·`tags` 같은 선택 필드의 기본값 처리와 향후 스키마 확장도 명확하다.

JSONL도 update/delete에서 전체 재작성이 필요하고 CSV보다 파일이 커질 수 있다는 단점이 있다. 이 애플리케이션은 이를 임시 파일 기록 → `flush`/`fsync` → `os.replace` 순서의 원자적 교체로 보완한다. CSV의 높은 외부 호환성은 버리지 않고 import/export 경계 포맷으로 사용한다. 즉, **내부 안전한 스트리밍 저장은 JSONL, 사용자 교환은 CSV**로 역할을 분리했다.

## 2. 측정 조건과 재현

저장소 루트에서 다음 한 줄을 실행한다. 표준 라이브러리만 쓰며 테스트 거래는 임시 디렉터리에만 생성된다. `--output`을 생략하면 같은 JSON을 터미널에 출력한다.

```bash
python -m scripts.benchmark_100k --records 100000 --repeat 3 --output profile-100k.local.json
```

| 항목 | 이 보고서의 조건 |
| --- | --- |
| 환경 | CPython 3.12.14, Linux 6.18.57 x86_64, glibc 2.41, 단일 프로세스 |
| 시작 데이터 | 매번 동일한 JSONL 100,000건, 16,445,890바이트(15.68 MiB). 12개월·8개 카테고리에 결정적으로 분포. ID는 등록 순서대로 고정 |
| 시간 | 매 측정 직전 원본 사본으로 복구. 생성·복사·GC를 제외한 서비스 호출부터 이터레이터 소진 또는 파일 쓰기 완료까지 `perf_counter()`로 3회 측정. CLI 표 출력은 제외 |
| 메모리·함수 측정 | 일부 연산에서 `tracemalloc`으로 Python 할당 최고치, 검색·수정에서 `cProfile`로 호출 수와 누적 시간 측정. 모두 별도 실행이므로 아래 벽시계 시간에는 계측 비용이 섞이지 않음 |
| 원본 대조 | JSON의 `seconds`는 개별 측정값, `median_s`는 중앙값. `fixture_sha256`은 입력 지문, `source_sha256`은 실행한 코드의 지문. 데이터 생성 비용도 별도 기록 |

복사 직후 실행하므로 OS 파일 캐시를 지운 콜드 스타트 시험은 아니다. 장치와 파일시스템이 다르면 초 단위 수치도 달라진다. 같은 입력에서는 처리 건수와 호출 수로도 동작을 대조할 수 있다.

## 3. 실측 결과

| 연산 | 3회 중앙값 | 확인한 처리 결과 |
| --- | ---: | --- |
| 최신 20건 목록 | 0.000220초 | 20건. 파일 끝에서 필요한 만큼만 읽음 |
| 식비 검색 | 0.500초 | 12,500건 일치 |
| 1월 요약 | 0.490초 | 8,344건 집계 |
| 없는 ID 조회 | 0.496초 | 없음 반환 |
| 가장 오래된 ID 수정 | 2.393초 | 지정한 1건의 메모 수정 |
| 가장 오래된 ID 삭제 | 1.936초 | 지정한 1건 삭제 |
| 1월 CSV 내보내기 | 0.517초 | 8,344건 기록 |
| 원자적 CSV 가져오기 | 0.532초 | **기존 100,000건에 신규 1,000건**을 한 번에 반영, 건너뜀 0건 |

별도 메모리 측정에서 목록은 **24.0 KiB**, 식비 검색은 **145.8 KiB**, 원자적 가져오기는 **10.35 MiB**였다. 앞의 두 연산은 거래를 순차 소비하지만, 가져오기는 기존·신규 ID를 집합에 유지한다. 이 수치는 전체 프로세스 RSS가 아니다.

### 어디서 시간을 쓰는가: cProfile

| 연산 → 함수 | 호출 수 | 누적 시간 | 해석 |
| --- | ---: | ---: | --- |
| 식비 검색 → `Transaction.from_dict` | 100,000 | 1.020초 | 반환된 12,500건뿐 아니라 모든 행을 모델로 변환·검증 |
| 식비 검색 → `json.loads` | 100,000 | 0.366초 | 카테고리 조건을 적용하기 전에 모든 줄 디코딩 |
| 가장 오래된 거래 수정 → `Transaction.from_dict` | 200,000 | 2.166초 | 대상 조회와 재작성에서 각각 100,000건씩 변환 |
| 같은 수정 → `_write_record` | 100,000 | 4.389초 | 바뀐 것은 한 줄이어도 임시 파일에는 전체 거래를 다시 직렬화 |

누적 시간에는 하위 호출 시간이 들어 있으므로 행끼리 합산하지 않는다. 프로파일러를 켠 실행의 시간은 위 3회 중앙값과 직접 비교하지 않는다. 전체 호출 경로와 자기 시간은 원본 JSON의 `cProfile`에서 볼 수 있다.

## 4. 병목별 개선안과 재검증 기준

아래에서 **계획**은 미구현이며 예상 효과를 실측 개선율로 제시하지 않는다. 거래의 원본은 계속 JSONL로 둔다.

| 병목과 코드 근거 | 구체적 개선안 | 같은 데이터에서 검증할 기준 |
| --- | --- | --- |
| **우선 1 · 수정/삭제**. [`TransactionRepository.update/delete`](../budget_app/repositories.py)가 전체 파일을 재작성. 수정에는 [`BudgetService.update_transaction`](../budget_app/services.py)의 선행 ID 조회까지 있음 | **계획:** 우선 조회·검증·수정을 한 순회로 합치고, 이후 월별/크기별 조각으로 분할. ID→조각 위치를 찾아 해당 조각만 임시 파일로 교체. 조회 인덱스만으로는 전체 쓰기가 없어지지 않음 | 수정 1건의 모델 변환 수(현재 200,000), 직렬화 수(100,000), 다시 쓴 바이트를 재측정. 대상을 제외한 조각은 바이트 불변이어야 함 |
| **우선 2 · 검색/ID 조회**. [`get`·`iter_transactions`](../budget_app/repositories.py)와 [`search_transactions`](../budget_app/services.py)에 위치 인덱스가 없어 O(n) | **계획:** 보조 인덱스에 ID→바이트 오프셋, 카테고리→오프셋 목록 저장. 대상만 `seek()`해 읽고, 원본 교체 후 세대 번호가 다르면 인덱스 재구축 | 없는 ID는 인덱스 조회로 끝나야 함. 식비 검색 시 모델 변환 수가 100,000에서 일치 후보 12,500 수준으로 줄고 결과·최신 등록 순서는 같아야 함 |
| **우선 3 · 월별 요약/내보내기**. 1월은 8,344건이지만 [두 연산](../budget_app/services.py) 모두 전체 거래를 순회 | **계획:** 월별 파일/오프셋으로 내보낼 범위를 제한. 요약은 월·카테고리 합계를 캐시하고, 거래 날짜나 금액을 수정하면 이전 달과 새 달 캐시를 모두 무효화 | 1월 내보내기 결과 8,344건·합계는 동일해야 함. 다른 달 행은 읽지 않는지, 월을 옮긴 직후 두 달의 잔액이 정확한지 검증 |
| **우선 4 · 일괄 가져오기**. [`_csv_transactions`](../budget_app/services.py)의 ID 집합은 조회를 줄이지만 기존 10만 건에서 최고 10.35 MiB 사용. [원자 반영](../budget_app/repositories.py)은 원본 크기만큼 임시 디스크도 필요 | **적용됨:** 행마다 ID 충돌을 찾기 위해 원본을 재검색하지 않고, 한 번 읽은 ID 집합을 배치에서 재사용. 원자 모드는 마지막에 한 번만 교체. **다음 계획:** 더 큰 규모에서는 디스크 기반 고유 ID 인덱스와 세대별 조각을 사용하되, 전체 배치 공개 시점은 하나로 유지 | 100만 건에서도 같은 신규 1,000건으로 최고 메모리·임시 쓰기량을 비교. 마지막 행 오류 및 교체 실패 때 기존 파일이 바이트 단위로 같아야 함 |

병렬화는 첫 조치가 아니다. 인덱스나 조각으로 읽는 양을 줄인 뒤에도 집계가 CPU에 묶일 때만, 독립된 조각을 프로세스별로 집계하고 부모 프로세스에서 합산한다. 동일 장치에서 직렬 실행과 비교해 시작 비용·디스크 경합을 포함해도 이득인지를 확인한다.

## 5. CSV 가져오기와 데이터 보존

같은 [예시 CSV](../tests/fixtures/mixed_import.csv)에는 정상 지출, 잘못된 금액, 정상 수입이 차례로 들어 있다. 기존 거래 6건에 이 파일을 가져오면 선택한 방식에 따라 결과가 달라진다.

| 방식 | 결과 | 파일에 기록하는 시점 |
| --- | --- | --- |
| 기본 `import` | 정상 2건을 추가하고 3행의 오류를 알린다. 기존 6건 → 8건 | 유효한 행마다 바로 추가한다. |
| `import --atomic` | 0건을 추가하고 종료 코드 2와 오류 원인을 반환한다. 6건 → 6건이며 기존 파일의 바이트가 같다. | 원본과 같은 디렉터리의 임시 파일에 쓴다. 모든 행이 유효할 때만 `flush → fsync → close → os.replace`로 한 번 교체한다. |

같은 [행 검증기](../budget_app/services.py)를 사용하며, 인용된 여러 줄짜리 값의 오류 번호는 CSV의 마지막 물리 줄을 가리킨다. 따옴표가 닫히지 않아 레코드 경계를 찾을 수 없으면 읽기를 중단한다. 원자 모드에서는 [파일 교체](../budget_app/repositories.py) 이전의 오류가 거래 원본을 바꾸지 않는다. 단일 작성자의 거래 파일에 대한 보장이며, 명령 로그나 다른 프로세스의 쓰기까지 되돌리지는 않는다.

[가져오기 테스트](../tests/test_csv_atomic.py)는 정상 배치가 한 번만 반영되는지, 잘못된 행이나 파일 쓰기·교체 실패 시 원본 내용이 그대로인지 검사한다. 저장소 루트에서 `python -m unittest -v tests.test_csv_atomic`으로 실행할 수 있다.
